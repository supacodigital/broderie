## 🔴 BLOQUANT — à corriger avant toute ouverture publique

### B1 — TVA : tous les produits seedés au taux hôtelier 3.8 % au lieu de 8.1 %
**`database/broderie.sql:655-658` + tous les `INSERT INTO products`**
`tax_rates` insère `id=1` → 8.1 % (normal), `id=2` → 2.6 %, `id=3` → 3.8 % (hôtelier).
**Tous les produits ont `tax_rate_id = 3`** → fil à broder, kits, toiles facturés à **3.8 %**.
- **Risque** : déclaration TVA AFC erronée, TVA sous-perçue sur chaque vente, factures fausses.
- **Correctif** : `UPDATE products SET tax_rate_id = (SELECT id FROM tax_rates WHERE category='standard')` — et corriger le seed / le script d'import produits à venir. Contrôle : `SELECT p.sku, tr.rate FROM products p JOIN tax_rates tr ON tr.id=p.tax_rate_id LIMIT 5;` doit rendre `8.10`.

### B2 — IDOR paiement : un client crée un PaymentIntent pour la commande d'autrui
**`backend/controllers/payment.controller.js:7,21` · `services/payment.service.js` · `routes/payments.routes.js:15-18`**
`createCardIntent(orderId)` / `createTwintIntent(orderId)` appellent `orderRepository.findById(orderId)` **sans `userId`**. Routes en `requireAuth` seul.
- **Exploitation** : A énumère les `orderId` (entiers séquentiels), `POST /payments/card/<orderId de B>` → écrase `payments.provider_payment_id` de B, récupère le `client_secret` et le montant de B, casse le rapprochement du webhook.
- **Correctif** (15 min) : passer `req.user.id` au service → `orderRepository.findById(orderId, userId)`, `404` si null.

### B3 — Avis produits : dépôt sans achat, sans limite, sans validation
**`backend/controllers/review.controller.js:22-36` · `repositories/review.repository.js:85-92` · `routes/reviews.routes.js`**
`create` insère `{userId, productId, rating, title, body}` : aucune vérif d'achat, pas de `UNIQUE(user_id, product_id)`, `rating` accepte `4.5`/`{}`, `title`/`body` sans longueur max. Les avis approuvés sont servis **publiquement** sur la home.
- **Exploitation** : bourrage d'avis 5★ auto-promo / 1★ concurrents ; payload XSS stocké dans `body` en pariant sur une modération rapide.
- **Correctif** (1-2 h) :
  1. Exiger l'achat : `SELECT 1 FROM order_items oi JOIN orders o ON o.id=oi.order_id WHERE o.user_id=? AND oi.product_id=? AND o.status IN ('paid','delivered') LIMIT 1`
  2. `ALTER TABLE reviews ADD UNIQUE KEY uq_review_user_product (user_id, product_id)` + gérer le 409
  3. Zod : `rating: z.number().int().min(1).max(5)`, `title: z.string().trim().max(120).optional()`, `body: z.string().trim().max(2000).optional()`
  4. Vérifier l'échappement au rendu front (ou stocker déjà échappé)

### B4 — Facture QR sans numéro TVA / IDE du vendeur
**`backend/services/invoice.service.js` (~L110) · `config/env.js`**
La facture imprime nom + adresse vendeur mais **aucun `CHE-xxx.xxx.xxx TVA`**. Dès l'assujettissement (CA ≥ CHF 100 000), LTVA art. 26 al. 2 let. a l'exige. `MentionsLegales.jsx:13` : IDE « à compléter ».
- **Correctif** : ajouter `qrInvoiceVatNumber` dans `config/env.js`, l'imprimer sous l'adresse vendeur (PDF), l'afficher aussi dans MentionsLegales/CGV. **Si Julie n'est pas encore assujettie** : retirer toute mention de TVA (facture + checkout + CGV) jusqu'au seuil.

### B5 — Facture : ligne TVA agrégée avec un taux moyen fictif
**`backend/services/invoice.service.js:221-224`**
`blendedRate = ((taxAmount / subtotal) * 100).toFixed(1)` → affiche `TVA incluse (7.4%)`. Un taux composite n'est pas un taux légal → facture irrecevable pour la déduction d'impôt préalable d'un client B2B (LTVA art. 26 al. 2 let. e).
- **Correctif** : grouper les `order_items` par `tax_rate_snapshot`, une ligne par taux distinct (`TVA 8.10 % : CHF x.xx`). Tant que tout est au taux normal, afficher `TVA 8.10 % incluse : CHF x.xx` en dur (pas de calcul).

### B6 — Endpoints LPD droits d'accès / suppression absents
**`backend/routes/users.routes.js` · `controllers/user.controller.js` · `repositories/user.repository.js`**
CGV (`§8`) et MentionsLegales (`§4`) **promettent** l'accès / rectification / suppression / portabilité. Aucun endpoint : pas d'export de données perso, pas de suppression de compte, `deleted_at` jamais écrit.
- **Correctif** :
  - `GET /api/v1/users/me/export` → JSON (profil, adresses, commandes, avis, consentements, fidélité)
  - `DELETE /api/v1/users/me` → **anonymisation** (`email` → `deleted+{id}@…`, nom → « Compte supprimé », `password_hash`/`google_id` → NULL, `deleted_at=NOW()`, `is_active=0`), en **conservant** `orders`/`order_items`/`payments` (obligation comptable 10 ans, art. 958f CO), purge `addresses`/`carts`/`wishlist`, anonymisation des avis.
  - Vérifier que le login exclut `deleted_at IS NOT NULL`.

### B7 — Secrets dans l'historique git (poussé sur `origin/main`)
**Commits `0e3e7626` (initial), `6813157b` (retrait du tracking seulement)**
`git show 0e3e7626:backend/.env` expose : `STRIPE_SECRET_KEY` (sk_test_ réelle), `MAIL_PASSWORD` (Mailtrap sandbox réel), `DB_PASSWORD=root`. `e2e/.env.test` est **encore tracké** avec `TEST_ADMIN_EMAIL=admin@broderie.ch` + mot de passe → compte admin à mot de passe public si ce compte existe en prod.
- **Correctif** :
  1. **Roter** : clé Stripe test, mot de passe Mailtrap ; régénérer le couple `GOOGLE_CLIENT_ID`/secret par précaution
  2. **Purger** : `git filter-repo --path backend/.env --path frontend/.env --path e2e/.env.test --invert-paths` sur les 3 branches + `push --force` + re-clone par l'équipe
  3. `git rm --cached e2e/.env.test` + `.gitignore` ; s'assurer que `admin@broderie.ch` / `test.e2e@broderie.ch` n'existent **que** sur staging/test

### B8 — Secret JWT placeholder actif en dev + pas de garde anti-placeholder
**`backend/.env` · `config/env.js:5-6`**
Le `.env` dev contient encore `JWT_ACCESS_SECRET=change_me_access_secret_32_chars_min` (valeur du `.env.example`, **public**). `env.js` ne contrôle que la présence (pas l'entropie, contrairement à `MFA_ENCRYPTION_KEY`). Un `.env` mal copié en prod = quiconque forge `{id:1, role:"admin"}`.
- **Correctif** (30 min) :
  1. Régénérer les 2 secrets dev (`openssl rand -base64 64`)
  2. `env.js` : refuser au boot tout secret contenant `change_me` / `__` ou `< 32` car., pour `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `JWT_MFA_PENDING_SECRET`, `DB_PASSWORD`, `STRIPE_WEBHOOK_SECRET`
  3. Assert `JWT_MFA_PENDING_SECRET ≠ JWT_ACCESS_SECRET ≠ JWT_REFRESH_SECRET`

### B9 — Consentement cookies : jamais réellement enregistré
**`backend/routes/consent.routes.js` · `database/broderie.sql:638-651`**
Le front POST `{type, accepted, version}`, mais l'INSERT **n'insère jamais `accepted`** (colonne absente de la table). `session_id` est lu depuis un cookie `session_id` qui **n'existe pas** (le vrai est `cartSession`) → `NULL` → viole `session_id NOT NULL` → INSERT échoue pour tout anonyme → `catch {}` silencieux. En pratique : **presque aucun consentement journalisé**, et impossible de prouver un refus.
- **Correctif** :
  1. `ALTER TABLE consent_logs ADD COLUMN accepted TINYINT(1) NOT NULL` + l'insérer
  2. `session_id` nullable, ou lire/générer un vrai cookie de session
  3. remplacer le `catch {}` muet par un log serveur

## 🟠 HAUTE — à corriger rapidement (semaines qui suivent)

### H1 — Invalidation de session après reset / changement de mot de passe
**`backend/services/auth.service.js:275-285` · `controllers/user.controller.js:113-146`**
Refresh token JWT stateless 7 j, sans `token_version` ni table de sessions. Après « mot de passe oublié », les tokens volés restent valides 7 j.
- **Correctif** : `users.token_version INT DEFAULT 0`, inclus dans le refresh token, incrémenté à chaque changement de mdp, vérifié dans `refreshToken`.

### H2 — Hash IP consent : SHA-256 nu = réversible
**`backend/routes/consent.routes.js:15`**
SHA-256 non salé d'une IPv4 (~4,3 Md) se pré-calcule en minutes sur GPU → pseudonymisation non robuste au sens LPD.
- **Correctif** : `crypto.createHmac('sha256', env.consentIpPepper)` avec `CONSENT_IP_PEPPER` en `.env` (jamais commité). + utiliser `req.ip` (respecte `trust proxy`) au lieu du header `X-Forwarded-For` brut (falsifiable).

### H3 — XSS stocké potentiel : champs publics non contraints
**`backend/controllers/admin/category.controller.js` · `admin/tag.controller.js` · `admin/settings.controller.js:110-122` (`cgv`, `mentions_legales`) · `routes/legal.routes.js` (public)**
`req.body` pris brut, sans Zod, sans longueur, sans sanitisation. Servi publiquement (catégories, CGV). Si le front rend via `dangerouslySetInnerHTML` → XSS persistant sur toutes les pages. Portée limitée aujourd'hui (1 seul admin de confiance) mais aggravée par la CSP faible (H8).
- **Correctif** : Zod (`z.string().max(...)`) partout ; pour les champs volontairement HTML (CGV) → `sanitize-html` (allow-list) avant stockage ; valider le format de `category.imageUrl`.

### H4 — Performance catalogue : `LEFT JOIN reviews` + `GROUP BY` sur 14k produits
**`backend/repositories/product.repository.js:108-127` (`findAll`), `197-223` (`search`), `242-262` (`findByCategoryId`)**
Les 3 listes joignent `reviews` puis `GROUP BY p.id, …` (28 colonnes) → temporary table + filesort systématiques. ~80-250 ms sur une simple page catalogue → cible p95 < 200 ms non tenable. En prime, `minRating` (l.62-65) utilise une **2e** mécanique (sous-requête corrélée) pour la même donnée.
- **Correctif** : dénormaliser `products.rating_avg` / `rating_count`, recalculées à l'approbation/suppression d'un avis. Supprimer le `LEFT JOIN reviews` **et** le `GROUP BY` des 3 requêtes.

### H5 — Performance : `srcSet` mort sur la fiche produit → images pleine résolution
**`backend/repositories/product.repository.js:295-300` (`findBySlug`) vs `frontend/src/pages/Product/ImageGallery.jsx:53-56`**
`findBySlug` (page produit publique) sélectionne les images **sans `url_medium` / `url_large`** → `srcSet` vaut `undefined` → l'`<img>` sert toujours l'original 1200px+, sur mobile aussi. Les 3 tailles `sharp` ne servent à rien sur la page la plus importante pour le LCP.
- **Correctif** (XS) : aligner `findBySlug` sur `findById` — `SELECT id, url, url_medium, url_large, alt, sort_order, is_primary FROM product_images …`. + `fetchPriority="high"` sur l'image principale.

### H6 — Webhook Stripe : pas d'idempotence → double crédit fidélité
**`backend/services/payment.service.js:93-163`**
Signature bien vérifiée, montant recalculé serveur (bon). Mais `event.id` stocké nulle part → Stripe retente (jusqu'à 3 j) → `INSERT order_status_history` dupliqué, et `processOrderEarning` **crédite les points 2×** (le `tierAlreadyRewarded` protège les paliers, pas le `total_spend_chf` via `addTransaction` type `earn`). Le crédit fidélité est lancé non-`await`é hors transaction (perdu si crash).
- **Correctif** : table `stripe_webhook_events (event_id PK, processed_at)` + `INSERT IGNORE` en tête de `handleWebhook` ; crédit fidélité **dans** la transaction ou en file avec retry ; `INSERT order_status_history` conditionné à un vrai changement de statut.

### H7 — SQL hors `repositories/` : 7 violations de l'architecture
**`routes/consent.routes.js:20` · `routes/legal.routes.js:6-13` · `controllers/admin/order.controller.js:48-82` · `controllers/admin/shipping.controller.js:111-114` · `services/payment.service.js:112-140` · `services/shipping.service.js:174-177`**
Des routes, controllers et services écrivent du SQL brut (dont des transactions) au lieu de passer par un repository. Casse l'invariant `routes → controllers → services → repositories`.
- **Correctif** (faible effort) : déplacer chaque requête dans le repository adéquat (`orderRepository.updateStatusTransactional(...)`, `orderRepository.markPaid(...)`, `orderRepository.saveShippingLabel(...)`) ; créer `consent.{controller,service,repository}.js`. Commencer par `consent.routes.js` (le pire).

### H8 — CSP : `script-src 'unsafe-inline' 'unsafe-eval'`
**`backend/app.js:55-69`**
Neutralise l'essentiel de la protection XSS de la CSP. Vite en build **n'a pas besoin** de ces directives (bundles statiques). Facteur aggravant direct des failles XSS (B3, H3).
- **Correctif** : retirer `'unsafe-eval'` ; remplacer `'unsafe-inline'` par hashes/nonces. Tester d'abord sans `unsafe-eval`.

### H9 — Migrations BDD : historique supprimé, aucun tracking, non idempotentes
**`database/migrations/` (2 fichiers sans n°) · commit `ca261ea9` a supprimé les migrations 001→012**
Pas de table `schema_migrations`, pas d'outil, migrations `DROP FOREIGN KEY` / `ADD COLUMN` sans garde `IF NOT EXISTS` → rejouer = erreur. `broderie.sql` contient déjà l'état post-migrations → 2 chemins (from-scratch vs existant) qui peuvent diverger.
- **Correctif** : adopter `umzug` + `mysql2` (léger, pas un ORM) avec table de tracking ; numéro d'ordre ou timestamp complet ; migrations idempotentes ; décider si `broderie.sql` est **généré** (`mysqldump --no-data`) ou un snapshot documenté. Restaurer les 12 migrations depuis `ca261ea9^` pour la traçabilité.

### H10 — Couche service absente pour tout l'admin catalogue
**`controllers/admin/product.controller.js` (258 l.) · `admin/category.controller.js` · `admin/tag.controller.js` · `controllers/user.controller.js` · `contact.controller.js`**
Logique métier dans les controllers (unicité slug, politique mdp, invalidation cache) **et** dans les repositories (`category.admin.repository.js` **lève** les erreurs métier de hiérarchie 3 niveaux, détection de cycle). `contact.controller.js` court-circuite `email.service.js` (30 KB).
- **Correctif** : créer `product.admin.service.js`, `category.admin.service.js`, `tag.admin.service.js`, `user.service.js`, `contact.service.js`. Remonter validation / unicité / règles de hiérarchie / envoi d'email. Controllers = parsing + formatage + `next(err)`.

### H11 — Vérification d'email non contraignante
**`backend/services/auth.service.js:75-97`**
Tokens pleinement valides émis à l'inscription, `email_verified_at` reste NULL, aucune route ne bloque dessus. Permet la création massive de comptes jetables, le spam d'avis, la pollution de la base.
- **Correctif** : middleware `requireVerifiedEmail` sur `POST /orders` et `POST /products/:id/reviews` a minima.

### H12 — Aucun test frontend boutique
**`frontend/` : 0 test, aucun outillage** (pas de Vitest, pas de script `test`)
CLAUDE.md §11 exige Vitest + Testing Library sur panier / checkout / formulaires / auth. Le tunnel d'achat (60 %+ du trafic) n'est couvert que par les E2E.
- **Correctif** : outiller `frontend/` (Vitest, aligné sur `admin/`), couvrir Cart, Checkout, formulaires auth.
